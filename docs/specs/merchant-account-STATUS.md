## Assunções da MA5 (documentadas conforme AGENTS.md — opção mais conservadora)

| Decisão aberta | Resolução MA5 | Motivo |
|----------------|----------------|--------|
| Escopo de "Auth + Merchant Hub refatorados; Login O(1); remove scan cross-DB" (spec §8) | Login da conta merchant (`merchant_members`) passa a ser **O(1)** (uma consulta no master, `loginMerchantAccount`) e é **tentado primeiro** em `POST /auth/login` sem `tenantSlug`; o scan cross-DB (`findAdminTenantsWithEmail`/`loginMerchantHub`) **continua existindo como fallback** para e-mails que não pertencem a nenhuma conta merchant ativa | Sem signup self-service (MA6) não há forma de uma conta real (produção) existir em `merchant_members` — remover o scan agora quebraria 100% dos admins hoje em produção (só existem como tenant). Remoção definitiva do scan é MA8 (cutover) / MA9 (limpeza), como a própria spec §8 já planeja ("Remover após MA": `findAdminTenantsWithEmail`) |
| `GET /auth/my-stores` | Guard único `requireAccountSession` aceita **sessão de conta merchant** (`session.memberId` → query O(1) `stores WHERE merchant_id`) **ou** sessão parcial do Merchant Hub legado (`email`+`role admin` → scan, inalterado) | Uma única rota precisa servir os dois modelos até o cutover; o branch dentro do handler decide qual caminho usar, sem duplicar rota |
| `POST /auth/select-store` (loja dentro da conta merchant) | **Rota nova**, análoga a `select-tenant`; guard `requireMerchantMember` (só exige `session.memberId`, não `storeId`, pois é ela quem define `storeId`) | Não existia primitivo de seleção de loja para o modelo merchant (MA4 só criou `requireStoreSelected`, que exige `storeId` já setado — inadequado para a própria rota de seleção) |
| `POST /auth/clear-store` | **Rota nova** (não pedida explicitamente pela spec) — limpa só `storeId`/`storeSlug`, mantendo `memberId`/`merchantId` | Simetria com `clear-tenant` (usado pelo front legado para voltar ao hub); sem ela não haveria como uma conta MA com 1 única loja "trocar de loja" futuramente (MA6+, quando existir 2ª loja) sem deslogar |
| Login com credencial errada quando o e-mail **já é** de uma conta merchant | Retorna `401 UNAUTHORIZED` (ou `IP_BLOCKED`/`ACCOUNT_LOCKED`) **direto**, sem cair no fallback do scan tenant | Evita duplicar contagem de tentativas em dois sistemas de lockout para o mesmo e-mail e evita side-effects (registro de tentativa falha) em `tentativas_login` de tenants que nunca tiveram esse e-mail como admin |
| E-mail duplicado entre contas merchant (`merchant_members.email` só é `UNIQUE(merchant_id, email)`, não globalmente) | **Não tratado** — `findActiveMembersByEmail` retorna todas as ocorrências ativas; MA5 usa a primeira (ordenada por `id`) | Sem signup self-service (MA6) esse cenário não ocorre na prática; validação de e-mail único (ou suporte formal a múltiplas contas por e-mail) fica para MA6 quando o cadastro for implementado |
| Rate limiting do login da conta merchant | Nova tabela **master** `login_attempts` (bloqueio por IP, mesmo algoritmo de `tentativas_login`) + colunas `failed_attempts`/`blocked_until`/`last_access_at` em `merchant_members` (bloqueio por conta) | `db-schema-english.md` §4 já recomendava `login_attempts` no master "quando o fluxo de auth for de fato religado" (adiado em MA2/MA3) — MA5 é essa fase; paridade de segurança com o modelo tenant (`tentativas_login` + `usuarios.tentativas_falha`) sem relaxar proteção (regra "Segurança nunca relaxar") |
| Bloqueio por IP do login merchant é **global** (tabela única no master, não por merchant) | Mantido assim (não replicado por merchant) | Ao contrário do tenant (bancos físicos separados = bloqueio efetivamente isolado por loja), o login da conta merchant é um único endpoint compartilhado por todas as contas; bloqueio global por IP é mais conservador contra brute-force cross-conta, sem abrir uma exceção de segurança |
| Campos de resposta `merchant`/`store` no JSON de `/auth/login`, `/auth/me`, `/auth/my-stores` (modelo merchant) | pt-BR (`{ slug, nome }`), mesmo padrão de `tenant.lojaNome` já usado | Decisão #4 da spec (§11, JSON EN vs pt-BR) permanece **aberta**; MA5 não a resolve — mantém consistência com os payloads existentes (`usuario.nome`, `tenant.lojaNome`) em vez de introduzir um padrão misto |
| Migração das rotas admin (`/api/v1/admin/*`) para `storeId`/`merchantDb` | **Não migradas** — continuam no modelo tenant legado (`tenantSlug`/`request.drizzle`) | Fora do escopo de "Auth + Merchant Hub"; migrar ~15 módulos exigiria uma fase própria e não há nenhuma conta merchant real em produção ainda (MA6 é pré-requisito) |
| Frontend admin (`apps/admin`) | **Não alterado** — Merchant Hub React continua 100% no fluxo `tenantSlug`/`select-tenant` | Mesmo padrão das fases MA3/MA4 (primitivos de API primeiro, sem rota HTTP viva no front); wiring do front ao modelo merchant fica para quando houver conta real via signup (MA6+) |
| Testes vitest desta sessão | **Escritos mas não executados neste ambiente** (sandbox sem Docker/Postgres disponível) | Mesma limitação documentada na MA2; rodar `make db-up-d && pnpm --filter api test` para validar `auth.merchant-login.test.ts` (12 casos novos) + regressão completa antes de mesclar |
